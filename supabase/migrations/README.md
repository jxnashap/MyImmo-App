# Migrationen — Regeln & Historie

## Baseline (ab 28.07.2026)
`20260728120000_baseline_schema.sql` ist ein **Snapshot des kompletten
Live-Schemas** — 42 Tabellen, 161 Constraints, 113 Indizes, 78 RLS-Policies und
14 Funktionen (davon 11 SECURITY DEFINER). Vorher lag nur ein Bruchteil davon im
Repo: Das Fundament (`properties`, `mieter`, `einnahmen`, `kosten`) und vor allem
**sämtliche RLS-Policies** existierten ausschließlich in der Datenbank. Damit war
die Zugriffskontrolle der App weder reviewbar noch reproduzierbar — und alle
Server-Actions verlassen sich darauf.

Die Datei ist idempotent und wurde gegen ein leeres PostgreSQL 16 verifiziert;
Spalten- und Policy-Hash stimmen exakt mit der Produktionsdatenbank überein. Sie
ist ein Snapshot, **kein nachgespieltes Änderungsprotokoll**: Die Alt-Migrationen
unten bleiben die Historie, die Baseline ist der reviewbare Ist-Stand und der Weg,
die Datenbank aus dem Repo neu aufzubauen.

Ab hier gilt die Regel unten wieder unverändert für jede weitere Änderung.

## Die Regel (ab 19.07.2026, verbindlich)
Jede Schemaänderung läuft über **zwei Schritte, immer beide**:
1. `apply_migration` (Supabase MCP) — führt aus und versioniert in
   `supabase_migrations.schema_migrations` (Version + Name + Statements).
2. **Dieselbe SQL als Datei hier ablegen**: `supabase/migrations/<version>_<name>.sql`
   (Version = von apply_migration vergebener Zeitstempel `YYYYMMDDHHMMSS`).

Kein direktes `execute_sql` für DDL. Kein Schema-Edit ohne Repo-Datei im selben PR.

## Historie exportieren (bei Bedarf)
Die vollständige SQL aller Alt-Migrationen liegt in der Prod-DB:
```sql
select version, name, statements
from supabase_migrations.schema_migrations
order by version;
```
Einzelne Datei nachziehen: Statement(s) der Version in `<version>_<name>.sql` kopieren.

## Bekannte Schema-Schulden (bewusst offen)
- `kosten.mieter_id` ist `text` (statt uuid-FK auf `mieter.id`) — Altlast, Fix = Datenmigration.
- `termine.prop_id` ist `text` — dito.
- `supabase/schema.sql` ist veraltet; `schema-reference.sql` ist Doku, keine Quelle der Wahrheit.

## Lokale Test-Datenbank (seit 11.10.2026, Prüfstand B18)

`scripts/db/testdb.sh` baut aus Baseline + allen Migrationen eine LEERE PostgreSQL-16-Datenbank
(Supabase-Nachbildung: `supabase/test/supabase_stubs.sql` — Rollen, `auth.uid()` aus
`request.jwt.claims`, `auth.users`, Storage-Tabellen). Vier Demo-Migrationen scheitern dort
erwartungsgemäß (`supabase/test/ausnahmen.txt`: sie setzen das LIVE-Demo-Konto voraus).
`scripts/db/rlstest.sh` führt `supabase/test/rls/*.sql` aus — Rollentests mit synthetischen Konten
(`pruef-…@myimmo.test`), jede Datei in einer zurückgerollten Transaktion; am Ende wird geprüft, dass
kein Testkonto liegen bleibt.

**Abgleich mit der Produktion (nur lesend):** `supabase/test/fingerabdruck_summe.sql` lokal und per
`execute_sql` in der Produktion ausführen. Stand 11.10.2026 gleich für Tabellen (67), Regeln (271),
Tabellenrechte, RLS (63), Trigger (82), Sichten (4), Indizes (162) und alle Funktionsrümpfe (ohne
Kommentare/Groß-Kleinschreibung verglichen). Unterschiede nur bei Ausführungsrechten → 20261011104000.
**Grenze:** Kein GoTrue — Anmeldung, TOTP und aal-Vergabe prüft diese Datenbank nicht; die Tests setzen
die Claims selbst.

**Regel: Eine neue RLS-Regel oder SECURITY-DEFINER-Funktion bekommt eine Datei in `supabase/test/rls/`
mit positiver UND negativer Probe je Rolle.** Mutationsprobe: die Zielmigration beim Aufbau auslassen
(`OHNE_MIGRATION=<datei>`), die mutierte Fassung einspielen — sonst bleibt z. B. ein REVOKE der echten
Fassung bestehen, und die Probe ist blind (am 11.10.2026 so passiert).

**In der CI (seit 11.10.2026):** Job `datenbank` in `.github/workflows/ci.yml` — PostgreSQL 16 als Dienst,
dann `testdb.sh` → `rlstest.sh` → `nebenlaeufig.sh`. Jeder Pull Request baut die Datenbank damit aus dem Repo
neu; eine Migration, die nur in der Produktion „funktioniert“, oder eine Rolle, die mehr darf als ihre
Rollentests erlauben, macht die CI rot. **Bekannte Grenze:** vier Demo-Migrationen setzen das Live-Demo-Konto
voraus und stehen in `supabase/test/ausnahmen.txt` (sie scheitern „erwartet“); die Supabase-Nachbildung ist
kein echtes GoTrue/PostgREST (kein Login, keine JWT-Signatur, keine Storage-Regeln).
